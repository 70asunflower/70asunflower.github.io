### 5. WSC 主机网络的关键需求

---

#### 5.1 high throughput：高吞吐

现代服务器网络带宽越来越高：

- 25G；
- 50G；
- 100G；
- 200G；
- 400G；
- 800G。

主机网络必须能以线速处理包。

否则会出现：

```text
NIC 很快
主机协议栈很慢
CPU 成为瓶颈
```

---

#### 5.2 low latency：低延迟

很多服务对延迟敏感，例如：

- 搜索；
- 广告；
- 数据库；
- RPC；
- 金融交易；
- 实时推荐；
- LLM prefill；
- 在线推理。

网络延迟包括：

- 协议栈延迟；
- 中断延迟；
- 调度延迟；
- NIC 处理延迟；
- 交换机排队延迟；
- 链路传播延迟；
- 拥塞延迟。

主机侧协议栈如果太重，会显著增加延迟。

---

#### 5.3 low tail latencies：低尾延迟

WSC 中尾延迟比平均延迟更重要。

因为一个用户请求常常触发很多内部 RPC。

例如：

```text
一次搜索
→ 几十个后端服务
→ 几百个内部调用
→ 只要少数调用慢
→ 整体响应变慢
```

所以系统关心：

- p50；
- p90；
- p99；
- p99.9；
- p99.99。

网络中的微突发、拥塞、重传、CPU 抢占、虚拟化噪声都可能导致尾延迟。

---

#### 5.4 traffic shaping：流量整形

原文提到：

> pacing and rate limiting

traffic shaping 包括：

##### pacing

把包更平滑地发出去，避免瞬时 burst。

例如不要一次性发一大波包，而是均匀发送。

好处：

- 减少交换机队列溢出；
- 降低拥塞；
- 降低丢包；
- 改善尾延迟。

##### rate limiting

限制租户、VM、容器或服务的速率。

好处：

- 多租户公平；
- 防止噪声邻居；
- 保护网络；
- 计费；
- QoS。

---

#### 5.5 OS-bypass：绕过操作系统

OS-bypass 指让数据路径绕过传统内核协议栈。

常见技术包括：

- DPDK；
- RDMA；
- user-space networking；
- kernel bypass；
- SR-IOV；
- virtio offload。

好处：

- 降低延迟；
- 提高吞吐；
- 减少 CPU 开销；
- 减少内核路径抖动。

挑战：

- 安全隔离；
- QoS；
- 监控；
- 调试；
- 策略执行；
- 虚拟化集成。

所以 OS-bypass 不能简单地“绕过一切”，而需要 NIC/IPU 在硬件中执行控制和策略。

---

#### 5.6 stringent security：严格安全

云网络必须处理：

- 租户隔离；
- 加密；
- 认证；
- 访问控制；
- 防攻击；
- 防 VM escape；
- 防侧信道；
- 防固件攻击；
- 零信任。

主机网络必须保证：

```text
一个租户不能看到/影响另一个租户
```

---

#### 5.7 line-rate encryption：线速加密

如果网络是 200Gbps，软件加密可能消耗大量 CPU。

所以需要 NIC/IPU 硬件加密，实现：

```text
200Gbps 线速加密
```

常见加密包括：

- IPsec；
- MACsec；
- TLS；
- storage encryption；
- virtual network encryption。

线速加密的意义是：

> 安全不应该以显著牺牲性能为代价。

---

#### 5.8 debuggability：可调试性

网络卸载后，调试会变难。

因为包处理可能发生在：

所以需要：

否则一旦出问题，很难定位。

#### 5.9 QoS：服务质量

QoS 用于区分不同流量优先级。

例如：

- 控制平面流量；
- 存储流量；
- RPC 流量；

QoS 可以通过：

#### 5.10 congestion control：拥塞控制

数据中心网络非常容易出现拥塞。

拥塞会导致：

- 尾延迟恶化；

#### 5.11 low host CPU use：低主机 CPU 占用

这是公有云特别关键的一点。

如果网络处理消耗大量 host CPU，会出现：

```text

```

#### 5.12 virtualization 和 VM migration

公有云还需要：

- VM live migration；

- 热升级。

这些功能如果都跑在 host CPU 上，会非常重。

### 6. onload 与 offload：两种互补方法

原文说：

> These requirements can be met with two complementary approaches: onload and offload.

这是主机网络设计的核心权衡。

---

#### 6.1 onload：利用 host CPU

原文：

> onload, where the host networking software leverages host CPU to provide low latency and rich features.

onload 的意思是：

> 把网络处理放在 host CPU 上，用软件实现丰富功能。

优点：

- 灵活；
- 功能丰富；
- 容易迭代；
- 低延迟用户态路径；
- 可编程性强；
- 适合快速创新。

例子：

- host-side traffic shaping；
- user-level TCP；
- DPDK；
- kernel bypass；
- software virtual switch。

缺点：

- 消耗 host CPU；
- 可能影响客户 workload；
- 安全边界较弱；
- 多租户隔离复杂；
- 峰值开销可能很高。

---

#### 6.2 offload：利用 NIC/IPU 硬件

原文：

> offload that uses compute in NIC cards for functions such as packet processing and cryptographic functions.

offload 的意思是：

> 把网络、存储、安全、虚拟化等功能卸载到 NIC/SmartNIC/IPU。

优点：

- 减少 host CPU 开销；
- 提高安全隔离；
- 支持线速处理；
- 支持 bare-metal；
- 改善多租户；
- 降低 TCO。

缺点：

- 硬件迭代慢；
- 可编程性受限；
- 调试更复杂；
- 固件/硬件安全要求高；
- 需要强软件栈配合。

---

#### 6.3 为什么两者互补？

因为完全软件化太耗 CPU，完全硬件化又不够灵活。

理想方式是：

```text
稳定、高频、线速路径 → hardware offload
复杂、低频、策略路径 → software control
```

例如：

- 包转发：硬件；
- 加密：硬件；
- checksum：硬件；
- QoS 队列：硬件；
- 虚拟设备映射：硬件；
- 控制策略：IPU 软件；
- 异常处理：软件；
- 新协议实验：软件。

### 7. SmartNIC、DPU、IPU 的关系

这一节出现了很多类似概念。

可以粗略理解：

|名称|含义|
| ----------| --------------------------------------------------|
|NIC|普通网卡|
|SmartNIC|智能网卡，具备一定包处理/卸载能力|
|DPU|Data Processing Unit，数据处理单元|
|IPU|Infrastructure Processing Unit，基础设施处理单元|

它们的核心趋势都是：

> 把原本由 host CPU 承担的基础设施功能移到网卡侧专用处理器。

这些功能包括：

- 网络虚拟化；
- 存储虚拟化；
- 加密；
- 压缩；
- QoS；
- telemetry；
- 安全；
- 设备虚拟化；
- 监控；
- 管理；
- live migration。

Google 这里讲的是 IPU。

### 8. Google IPU 的关键思想：分离 control plane 和 data plane

原文说：

> One key tenet of Google’s IPU approach is to separate the server control plane from the server data plane on the same set of CPU cores.

这句话需要仔细理解。

传统服务器中，很多东西都跑在 host CPU 上：

```text
customer workload
+ virtualization
+ network processing
+ storage processing
+ logging
+ monitoring
+ container lifecycle
+ security agents
```

也就是说：

> 客户 workload 和云基础设施控制功能共享同一组 CPU cores。

这会带来两个问题：

1. 性能干扰；
2. 安全风险。

IPU 的目标是：

```text
host CPU：运行客户 data plane / workload
IPU：运行 server control plane / infrastructure functions
```

---

### 9. server control plane 负责什么？

原文说：

> The server’s control plane is responsible for monitoring the server, virtualizing hardware resources, container lifecycle, network and storage I/O processing, logging, and a growing list of other functionality unrelated to running customer workloads.

server control plane 包括：

- 服务器监控；
- 硬件资源虚拟化；
- 容器生命周期；
- 网络 I/O 处理；
- 存储 I/O 处理；
- 日志；
- 安全代理；
- 设备管理；
- 远程管理；
- telemetry；
- 策略执行；
- live migration；
- 虚拟化控制。

这些功能对客户 workload 很重要，但它们本身不是客户 workload。

可以理解为：

```text
customer data plane：客户程序真正处理的数据
server control plane：云平台为了运行/管理/隔离/监控这些程序所做的事
```

---

### 10. 为什么虚拟化控制开销很严重？

原文说：

> Without optimization, server control and virtualization overheads can be significant, in some cases bursting to more than 50% of overall compute capacity.

这是一个非常惊人的数字。

如果不优化，控制和虚拟化开销可能瞬间超过 50% 计算容量。

这意味着：

```text
客户以为买了一台机器
实际上可能一半 CPU 在跑云基础设施
```

这会带来两个糟糕选择。

---

#### 10.1 按峰值静态预留

如果按峰值预留：

```text
预留大量 CPU 给控制平面
```

结果：

- 成本很高；
- 资源浪费；
- 客户可用资源少；
- TCO 不可接受。

---

#### 10.2 按平均值限制

如果按平均值限制控制平面：

```text
平时够用
峰值时控制平面被 throttle
```

结果：

- 网络/存储/管理性能波动；
- 尾延迟恶化；
- 监控丢数据；
- 虚拟化控制不稳定；
- 系统可靠性下降。

---

### 11. 安全问题：虚拟化 bug 可能导致 host root 被攻破

原文：

> running the control plane on the same CPU alongside customer workloads introduces security risks if malicious guests can find and exploit virtualization bugs to become root on the host CPU.

如果控制平面和客户 workload 跑在同一 CPU 上，那么恶意租户可能：

1. 发现虚拟化漏洞；
2. 从 VM/container 逃逸；
3. 获取 host root；
4. 控制整台机器；
5. 访问其他租户数据；
6. 篡改云平台组件。

这就是所谓的：

```text
VM escape / container escape
```

所以必须把客户 workload 和云基础设施控制平面隔离到不同信任域。

这与 6.2.3 讲的 arena 和 hardware trust boundary 完全一致。

#### 12.1 DC-SCM 提供 Root-of-Trust

原文：

> a secure control module DC-SCM attached to the IPU provides the root of trust RoT of the entire machine along with integrated RoTs of the attached CPUs.

DC-SCM 与 IPU 连接，提供整机可信根。

同时 CPU 也有集成的 RoT。

这意味着机器启动和运行时需要证明：

- IPU 固件可信；
- CPU 固件可信；
- BIOS/UEFI 可信；
- BMC/DC-SCM 可信；
- PCIe 设备固件可信；
- 管理平面可信。

### 18. 可以用来检验理解的问题

---

#### 问题 1：为什么网络是 WSC 的基础？

因为 WSC 是跨 tray、rack、cluster、data center、campus、region 的分布式系统。

几乎所有关键操作都依赖网络：

- RPC；
- 存储；
- 训练；
- 复制；
- 调度；
- 监控；
- 用户请求；
- 安全认证。

网络性能直接决定系统性能、可用性和成本。

---

#### 问题 2：一个数据包从应用到 Internet 会经过哪些层次？

大致路径：

```text
application
→ host networking stack
→ NIC/SmartNIC/IPU
→ ToR
→ cluster fabric
→ data center fabric
→ campus/WAN
→ edge/ISP/Internet
```

---

#### 问题 3：为什么主机网络需要低 host CPU 使用？

因为如果网络/存储/虚拟化消耗太多 host CPU，会：

- 降低客户可用性能；
- 增加成本；
- 降低利用率；
- 影响尾延迟；
- 降低云产品竞争力。

---

#### 问题 4：onload 和 offload 的区别是什么？

onload：

- 用 host CPU 和软件做网络处理；
- 灵活、功能丰富；
- 但消耗 host CPU。

offload：

- 用 NIC/SmartNIC/IPU 硬件做处理；
- 降低 host CPU 开销；
- 提高线速能力和安全隔离；
- 但硬件迭代和调试更复杂。

---

#### 问题 5：server control plane 和 server data plane 分别是什么？

server control plane：

- 监控；
- 虚拟化；
- 容器生命周期；
- 网络/存储 I/O 控制；
- 日志；
- 安全策略。

server data plane：

- 客户 workload 的实际计算和数据访问。

---

#### 问题 6：为什么要把 control plane 从 host CPU 移走？

因为不移动会导致：

- 虚拟化开销可能超过 50% CPU；
- 客户性能下降；
- 峰值难以预留；
- 平均限制又会影响稳定性；
- 恶意租户可能利用虚拟化漏洞逃逸到 host。

IPU 可以把控制平面放到独立硬件域。

---

#### 问题 7：IPU 为什么包含 PCIe switch？

因为 IPU 需要管理和虚拟化多种 PCIe 设备：

- NIC；
- SSD；
- GPU；
- TPU；
- 加密加速器；
- 压缩加速器。

PCIe switch 使 IPU 可以：

- 做物理到虚拟设备映射；
- 隔离租户；
- 支持 live migration；
- 做资源解耦；
- 快速接入商用设备。

---

#### 问题 8：Titanium IPU 的关键特点是什么？

Titanium IPU：

- 是 Google 第一代 IPU；
- PCIe add-in card；
- 与 Intel 共同开发；
- 商用型号 Intel E2100；
- 200Gbps 网络；
- 16 个 ARM Neoverse N1 cores；
- 在 IPU 上运行 server control plane；
- 与 host data plane 物理分离；
- 提供 bare-metal 性能和更强安全。

> 6.4.2 聚焦主机网络和 SmartNIC/IPU。现代 WSC 主机网络有很多严格要求：高吞吐、低延迟、低尾延迟、traffic shaping、OS-bypass、严格安全、线速加密、可调试性、QoS、拥塞控制，并且要尽量低 host CPU 占用。公有云还必须支持虚拟化、租户隔离和 VM 迁移。为了同时满足这些要求，系统通常采用 onload 和 offload 两种互补方法。onload 利用 host CPU 和主机软件提供低延迟和丰富功能，offload 则利用 NIC 或 IPU 上的计算资源处理包处理、加密、虚拟化和存储等功能。
>
> Google 的 IPU 设计有一个关键原则：把 server control plane 和 server data plane 分离。传统上，监控、虚拟化、容器生命周期、网络/存储 I/O 处理、日志等控制功能会和客户 workload 一起运行在 host CPU 上。这会导致严重的虚拟化开销，有时甚至可能 burst 到超过 50% 的计算容量。如果按峰值预留资源，成本不可接受；如果按平均值限制，又会影响性能和稳定性。此外，控制平面和客户 workload 共享 CPU 还会带来安全风险，恶意 guest 可能利用虚拟化漏洞逃逸到 host root。
>
> 为了解决这些问题，Google 的 IPU 架构把 server control plane 放到 IPU 上运行，让 host CPU 主要运行客户 data plane。在这个架构中，DC-SCM 连接到 IPU，提供整机的 Root-of-Trust，CPU 也有集成 RoT。机器由 IPU、一个或多个 CPU/DRAM 模块，以及大量基于 PCIe SR-IOV 的 I/O 设备组成，包括 NIC、SSD、GPU/TPU 和加密、压缩等加速器。IPU 内部包含 PCIe switch，并硬件加速物理设备到虚拟设备的映射、live migration 和 tenant isolation。这样，系统可以快速采用商用 CPU 和 I/O 设备，同时不牺牲安全、隔离和性能。
>
> Google 的第一代 Titanium IPU 是 PCIe 插卡，与 Intel 共同开发，商用型号为 Intel E2100。它提供 200Gbps 网络连接，并集成 16 个 ARM Neoverse N1 cores。IPU SoC 在物理分离的 offload compute complex 上运行 server control plane，从而给客户 workload 提供 bare-metal 性能，同时增强客户和 Google 的安全边界。将 NIC 和数据加速器集成到 IPU 中，还可以把网络和存储硬件加速与 offload 计算紧耦合，使硬件和软件包处理、命令处理能够灵活交织，支持 I/O 虚拟化和资源解耦，最终显著降低系统 TCO。
>
> 总体而言，这一节的核心结论是：WSC 网络不只是连接机器，而是把主机、机架、集群、数据中心和全球网络连接成一个高性能分布式系统。主机侧网络的关键趋势是通过 SmartNIC/IPU 将网络、存储、安全、虚拟化和控制平面从 host CPU 卸载出去，形成独立信任域和控制域，从而同时实现高性能、低 CPU 开销、强隔离、可迁移和低 TCO。
