上个月我在五个地方同时改同一个技能，改到第三处时忘了第一处改的是什么。当天晚上我把所有副本删了，重做成一个仓库。

## 副本是怎么烂掉的

一开始就是 `cp -r`。谁不会呢，复制到 `~/.claude/skills/` 就能用。

第一个月没事，因为只有两个 agent。后来装了 Gemini CLI、ZCode、WorkBuddy，每个都要一份。某个周末我改了 Claude 目录里那份的触发描述，忘了 Codex 目录里还有一份。两周后打开对比，六份内容各不相同——问题不在于内容不一样，而在于**我分不清哪份是对的**。它们都看起来像最新的。

复制这个动作本身没错，错在它把「同一份内容」变成了「六份各自演化的内容」，而且没有任何东西提醒你它们已经分岔。

## 换成一个仓库加目录联结

做法很简单：技能全部住在 `70asunflower-skills` 这一个 git 仓库里，各 agent 的 skills 目录里放的不是文件，是指向仓库子目录的联结。

Windows 上是 junction，Linux 和 macOS 上是 symlink。对 agent 来说完全透明——它打开 `~/.claude/skills/layoutfix/SKILL.md`，读到的是仓库里的那一份。

于是「改哪里」这个问题消失了：改哪个目录都是改同一个文件，git 管版本，没有第二份可以漂移。

## 三条不得不立规矩

这套结构会诱导人犯错，所以补了三条。

**不复制、不另存、不"先备份一份"。** 副本会立刻开始漂移。想要旧版本，`git show` 比 `_v2` 文件可靠得多。

**新技能建在仓库里，不在 agent 目录下建真实目录。** agent 的 skills 目录本身是真实目录，只有里面每一项是联结。你在那里 `mkdir` 出来的东西会脱离仓库，其他 agent 永远看不到——而且它长得和正常技能一模一样，你不会发现。

**删技能必须同步清理联结。** 这条最容易被忽略，因为它的后果不报错。

## 42 条断链

有一次我批量删了 7 个用不上的技能，`git rm -r` 干净利落。然后打开某个 agent 的技能列表，它们还在。

主库的目录没了，各 agent 里那条 junction 变成了指向空路径的空壳。不报错，不警告，行为不可预期。7 个技能乘 6 个 agent 目录，42 条断链。

所以现在有个硬规则：跑完 `doctor` 不返回「问题数: 0」，就不算做完。删除操作尤其不能只做一半。

## 判断一条链接有没有被纳管，比想象的难

这是排障时踩得最深的一个坑，值得单独说。

直觉是用 `os.path.isjunction()`。它确实能识别 junction，但链式嵌套同样返回 `True`——`workbuddy/x → zcode/x → 真实目录` 这种两跳的，和直连看起来一模一样。你以为纳管了，其实中间隔了一层，主库一改名整条链就断。

换成 `os.path.realpath()`？更糟。它把整条链解析到底，两跳和直连的结果完全相同，你连区分的机会都没有。

正确的做法是比对 `os.readlink()` 返回的**直接目标**是不是主库路径。只看第一跳。

顺带一个：`os.path.islink()` 对 junction 返回 `False`，别拿它判断。`find -name SKILL.md` 也不会跟随 junction，用它会得出"技能全丢了"的错误结论。

这些细节没有任何一条能靠推理想到，全是被误报和断链教出来的。

## 现在是什么样

28 个技能，一份文件，五个 agent。从论文写作、矢量图版面检查，到项目脚手架、思源笔记读写。

仓库里除了技能，还写了这套结构怎么维护：分发的脚本、体检的脚本、提交前的三道闸门、以及上面这些坑的来龙去脉。

代码和文档都在 [github.com/70asunflower/70asunflower-skills](https://github.com/70asunflower/70asunflower-skills)，MIT。

## 这套做法不只适用于技能

任何「同一份内容要给多个工具用」的场景都成立：dotfiles、编辑器配置、模型权重、共享提示词库。判据只有一条——**这份内容会不会因为被复制而分岔**。

会，就别复制。
