### 一、这一节在整本书中的位置：为什么数据中心需要 tracing？

这本书反复强调一个核心观点：

> 数据中心本身是一台计算机。

也就是说，单个服务器不再是程序运行的唯一边界。一个用户请求往往不是在某一台机器上完成，而是在成百上千台服务器之间协作完成。

因此，传统的单机性能分析工具不够用了。

例如：

- 单机上你可以用 `top`​、`perf`​、`strace`、profiler 看某个进程为什么慢。
- 但在数据中心里，一个请求可能经过：

  - 前端 Web 服务
  - 认证服务
  - 推荐服务
  - 购物车服务
  - 库存服务
  - 支付服务
  - 风控服务
  - 数据库
  - 缓存
  - 消息队列
  - 日志服务
  - 通知服务

如果一个用户点击“购买”后 5 秒才返回，问题到底在哪里？

可能是：

- 某个微服务慢；
- 某个数据库查询慢；
- 某个下游服务超时重试；
- 网络延迟高；
- 某个队列积压；
- 某台机器 GC 停顿；
- 某个锁竞争严重；
- 某个依赖服务降级；
- 某个副本过载；
- 某个调度策略导致请求排队。

这时只看 service-level dashboard 是不够的。

### 二、Dashboard 的局限：知道“慢了”，但不知道“为什么慢”

原文说：

> Although service-level dashboards help operators quickly identify service-level problems, they typically lack the detailed information required to know why a service is slow or otherwise not meeting requirements.

这句话可以拆成两层。

#### 1. Dashboard 擅长发现“症状”

例如仪表盘可以告诉你：

- QPS 下降了；
- P99 latency 上升了；
- 错误率升高了；
- 某个服务 CPU 飙高；
- 某个数据库连接池耗尽；
- 某个集群的 tail latency 异常。

这些都属于 service-level metrics，也就是服务级指标。

它们非常适合回答：

> 系统现在是不是有问题？

比如：

```text
Buy Service P99 latency: 200ms -> 3s
Error rate: 0.1% -> 8%
```

这能让你快速发现异常。

#### 2. Dashboard 不擅长解释“根因”

但仪表盘通常只能看到聚合指标。

例如你知道 `Buy Service` 慢了，但不知道它为什么慢。

因为一个服务慢，可能不是它自己慢，而是它调用的几百个下游中的某一个慢了。

例如：

```text
Buy Frontend
  -> Auth Service
  -> Cart Service
  -> Inventory Service
  -> Pricing Service
  -> Payment Service
      -> Fraud Detection Service
      -> Bank Gateway
  -> Order DB
  -> Notification Service
```

如果最终用户看到慢，可能是 `Fraud Detection Service`​ 里面某个模型推理慢了，也可能是 `Bank Gateway` 网络抖动。

Dashboard 往往只能看到：

```text
Buy Service latency high
```

但看不到：

```text
Buy Service 慢是因为 Payment Service 调用了 Fraud Detection Service，
Fraud Detection Service 在某个特征查询上等待 Redis 超时，
而 Redis 所在机器正在做快照导致延迟升高。
```

这就是 tracing 要解决的问题。

### 三、从 Monitoring 到 Observability：tracing 的关键意义

原文有一句很重要：

> Distributed system tracing tools address this need, and form an important step in moving from monitoring to observability.

这里涉及一个现代系统工程中非常重要的概念：

#### 1. Monitoring：监控

Monitoring 更偏向于：

> 我预先定义好要看哪些指标，当指标异常时告诉我。

例如：

- CPU 使用率超过 80% 告警；
- 错误率超过 1% 告警；
- P99 延迟超过 500ms 告警；
- 磁盘使用率超过 90% 告警。

它适合已知问题模式。

也就是说，你必须事先知道：

- 哪些指标重要；
- 什么阈值算异常；
- 哪些故障模式可能发生。

#### 2. Observability：可观测性

Observability 更强调：

> 即使我没有预先想到某个问题，也可以通过系统外部输出来推断系统内部状态。

在分布式系统中，可观测性通常包括三大支柱：

```text
Metrics  指标
Logs     日志
Traces   调用链
```

这三者的关系可以粗略理解为：

|类型|回答的问题|例子|
| ---------| ------------------------------| --------------------------------|
|Metrics|系统整体怎么样？|P99 latency 升高|
|Logs|某个事件具体发生了什么？|某请求支付失败，错误码 500|
|Traces|一个请求在系统里经历了什么？|请求经过哪些服务，每段耗时多少|

Tracing 的价值在于，它把“一个请求”作为分析单位，把跨服务、跨机器、跨进程的行为串起来。

### 四、Tracing 到底追踪什么？

原文说：

> These tools attempt to determine all the work done in a distributed system on behalf of a given initiator such as a user request and detail the causal or temporal relationships among the various components involved.

这里有两个关键词。

#### 1. on behalf of a given initiator：为某个发起者完成的所有工作

例如用户点击“Buy”按钮，这个点击就是一个 initiator。

它可能触发一整棵调用树：

```text
User Click Buy
└── Frontend
    ├── AuthService.CheckToken
    ├── CartService.GetCart
    ├── InventoryService.CheckStock
    ├── PricingService.CalculatePrice
    ├── PaymentService.Charge
    │   ├── FraudService.Evaluate
    │   ├── BankGateway.Authorize
    │   └── LedgerService.Record
    ├── OrderService.CreateOrder
    └── NotificationService.SendConfirmation
```

Tracing 的目标不是只看 `Frontend` 自己做了什么，而是追踪这个用户请求引发的所有相关工作。

#### 2. causal or temporal relationships：因果关系或时间关系

Tracing 不只是记录“哪些事情发生了”，还要记录它们之间的关系。

##### 时间关系

例如：

```text
A 开始后，B 才开始。
C 在 D 结束前就开始了。
E 和 F 是并行的。
```

##### 因果关系

例如：

```text
Frontend 调用 PaymentService，
PaymentService 调用 FraudService，
FraudService 查询 Redis。
```

那么：

```text
Frontend -> PaymentService -> FraudService -> Redis
```

就是一条因果链。

如果 Redis 慢了，那么整条链上的请求都可能慢。

### 五、一个直观例子：用户点击“Buy”后发生了什么？

原文举例：

> when a user clicks the “Buy” button, the application front-end may transitively invoke hundreds of microservices in the process of completing the purchase.

这里的关键词是：

> transitively invoke

不是直接调用几百个服务，而是“传递性地调用”。

例如：

```text
Frontend 调用 A
A 调用 B 和 C
B 调用 D
D 调用 E
C 调用 F
F 调用 G
...
```

最终可能形成一棵很大的调用树。

假设用户点击 Buy 后失败或超时，问题可能是：

```text
Frontend
  -> OrderService
    -> PaymentService
      -> FraudDetectionService
        -> FeatureStore
          -> Redis
            -> 某台 Redis 节点正在做 BGSAVE，导致写延迟升高
```

如果没有 tracing，你可能只看到：

```text
Frontend timeout
```

或者：

```text
OrderService latency high
```

但有了 tracing，你可以看到：

```text
Trace ID: 7f3a9c2e

Span: Frontend /buy                3005ms
  Span: OrderService createOrder   2980ms
    Span: PaymentService charge    2950ms
      Span: FraudService evaluate  2900ms
        Span: FeatureStore get     2880ms
          Span: Redis GET          2870ms
```

这样你马上能看出：

> 瓶颈在 Redis GET，而不是 Frontend，也不是 PaymentService 自己的业务逻辑。

这就是 tracing 的根因定位能力。

### 六、Tracing 的核心数据模型：Trace 和 Span

原文没有直接展开，但理解 tracing 最好补充现代 tracing 的基本模型。

现代分布式追踪通常使用两个核心概念：

#### 1. Trace

一个 trace 表示一个完整请求的生命周期。

例如一次用户购买请求就是一个 trace。

每个 trace 通常有一个全局唯一 ID：

```text
trace_id = 4bf92f3577b34da6a3ce929d0e0e4736
```

#### 2. Span

一个 span 表示 trace 中的一段工作。

例如：

```text
Span: PaymentService.Charge
```

一个 span 通常包含：

```text
trace_id
span_id
parent_span_id
service name
operation name
start time
duration
tags
logs
error status
```

例如：

```json
{
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "parent_span_id": "a1b2c3d4e5f60718",
  "service": "payment-service",
  "operation": "charge",
  "start_time": "2026-07-23T10:00:00.000Z",
  "duration_ms": 2950,
  "status": "error"
}
```

多个 span 通过 `parent_span_id` 组成树状或 DAG 结构。

例如：

```text
Frontend span
├── OrderService span
│   └── PaymentService span
│       └── FraudService span
│           └── Redis span
└── NotificationService span
```

### 七、原文提到的两类 tracing 工具：黑盒 vs 插桩

原文把 tracing tools 分成两大类：

```text
1. black-box monitoring systems
2. application/middleware instrumentation systems
```

这是这一节的重点。

---

### 八、第一类：Black-box monitoring systems

原文例子：

```text
WAP5
Sherlock
```

它们的方法是：

> observing networking traffic among system components and inferring causal relationships through statistical inference methods.

也就是说，它们不修改应用代码，而是观察网络流量。

---

#### 1. 黑盒监控的基本思想

假设你不知道服务内部怎么实现，也不知道哪个请求调用了哪个子请求。

你只能看到机器之间、服务之间的网络包或 RPC 消息。

例如你观察到：

```text
A -> B 请求
B -> C 请求
C -> D 请求
```

然后你通过统计方法推断：

```text
A 的请求很可能导致了 B、C、D 的行为。
```

这就是 black-box tracing。

它把系统组件当成黑盒：

```text
       network traffic
A  ---------------------->  B
B  ---------------------->  C
C  ---------------------->  D
```

它只看外部通信，不看内部函数调用。

---

#### 2. 黑盒方法的优点

原文说：

> these approaches have the advantage of working with no knowledge of, or assistance from, applications or software infrastructure components.

也就是说，它最大的优点是：

> 不需要应用配合。

这在现实中很有价值。

因为大型系统里可能有：

- 老系统；
- 第三方服务；
- 闭源组件；
- 不同语言写的服务；
- 已经没人维护的模块；
- 不方便改代码的服务。

如果你要求所有服务都插桩，成本可能非常高。

而黑盒方法只需要观察网络流量，例如：

- TCP 连接；
- HTTP 请求；
- RPC 调用；
- 消息队列流量；
- DNS 查询；
- 服务间通信时间戳。

因此它部署门槛较低。

---

#### 3. 黑盒方法的缺点

原文说：

> this approach inherently sacrifices information accuracy because all relationships must be statistically inferred.

关键词是：

> statistically inferred  
> 统计推断

也就是说，它不是明确知道：

```text
请求 X 导致了调用 Y
```

而是通过相关性推测：

```text
请求 X 很可能导致了调用 Y
```

这会带来几个问题。

##### 问题一：并发请求难以区分

如果同一时间有很多请求：

```text
User1 -> A -> B -> C
User2 -> A -> B -> C
User3 -> A -> B -> C
```

你只看到网络流量：

```text
A -> B
B -> C
```

很难确定某个 `B -> C` 到底属于 User1、User2 还是 User3。

##### 问题二：异步调用难以推断

如果系统使用消息队列：

```text
OrderService -> Kafka -> InventoryService
```

生产者和消费者之间可能隔了很久。

仅靠网络流量很难确定：

```text
某条 Kafka 消息是由哪个用户请求产生的？
```

##### 问题三：统计推断需要大量数据

为了提高准确率，需要收集更多消息数据。

但原文指出：

> Collecting and analyzing more messaging data can improve accuracy but at the expense of higher monitoring overheads.

也就是说：

```text
更高准确率
  <->
更多网络流量采集
  <->
更高监控开销
```

这是一个典型权衡。

##### 问题四：看不到服务内部细节

黑盒方法能看到：

```text
A 调用 B
B 响应慢
```

但可能看不到：

```text
B 内部哪个函数慢
B 内部哪条 SQL 慢
B 内部哪个锁等待久
B 内部哪个缓存 miss
```

因此它对根因分析的帮助有限。

---

### 九、第二类：Instrumentation-based tracing systems

原文例子：

```text
Pip
Magpie
X-Trace
```

它们的方法是：

> explicitly modify applications or middleware libraries for passing tracing information across machines and across module boundaries within machines.

也就是通过插桩，把追踪信息显式传递出去。

---

#### 1. 插桩 tracing 的基本思想

插桩 tracing 的核心是：

> 在代码或库中埋入追踪逻辑，让每个请求携带 trace context。

例如一个请求从 A 到 B 时，不只发送业务数据：

```text
Request:
  user_id = 123
  item_id = 456
```

还携带追踪信息：

```text
TraceContext:
  trace_id = abc123
  parent_span_id = spanA
  span_id = spanB
```

B 收到后继续调用 C：

```text
TraceContext:
  trace_id = abc123
  parent_span_id = spanB
  span_id = spanC
```

这样就能明确知道：

```text
spanA 是 spanB 的父节点
spanB 是 spanC 的父节点
```

不需要统计猜测。

---

#### 2. 插桩 tracing 的优点

原文说：

> These systems can be very accurate as there is no need for inference.

因为因果关系是显式传递的。

例如：

```text
trace_id = abc123

Frontend span
  parent: none

OrderService span
  parent: Frontend span

PaymentService span
  parent: OrderService span

FraudService span
  parent: PaymentService span
```

这不是推断出来的，而是系统明确记录下来的。

因此准确性高。

---

#### 3. 插桩 tracing 的缺点

原文说：

> they require all components of the distributed system to be instrumented to collect comprehensive data.

也就是说，如果要得到完整 trace，所有组件都要支持 tracing。

如果调用链是：

```text
A -> B -> C -> D -> E
```

其中 A、B、D、E 都插桩了，但 C 没有。

那么 trace 可能变成：

```text
A -> B -> ??? -> D -> E
```

中间出现黑洞。

你只知道 B 调用了某个东西，D 又出现了，但不知道中间 C 发生了什么。

这就是 instrumentation gap。

### 十、黑盒 vs 插桩：核心权衡

可以用下面这张表理解。

|维度|Black-box tracing|Instrumentation-based tracing|
| ------------------| ------------------------------| -------------------------------|
|是否需要修改应用|不需要|需要，或至少需要库支持|
|数据来源|网络流量、系统调用、外部行为|应用/中间件内部埋点|
|因果关系|统计推断|显式传播|
|准确性|较低，依赖推断|较高|
|部署难度|相对低|相对高|
|对老系统友好|友好|不友好，除非库统一|
|内部细节|少|多|
|开销|可能很高，尤其全量网络采集|可高可低，取决于采样和实现|
|典型代表|WAP5, Sherlock|Pip, Magpie, X-Trace, Dapper|

可以这样记：

```text
黑盒 tracing：
  不改代码，但只能猜。

插桩 tracing：
  要改代码或库，但能准确知道。
```

### 十一、Dapper 的意义：如何让插桩 tracing 大规模落地？

原文特别提到：

> The Dapper system is an annotation-based tracing tool that remains effectively transparent to application-level software by instrumenting a few key modules that are commonly linked with all applications, such as messaging, control flow, and threading libraries.

Dapper 是 Google 的分布式追踪系统，也是现代很多 tracing 系统的思想源头之一。

它的关键设计是：

> 不要求每个应用开发者手动到处埋点，而是插桩少数公共基础库。

---

#### 1. 为什么这很重要？

如果一个系统有几千个服务，让每个服务开发者都手动加 tracing 代码，成本很高：

```cpp
startSpan();
...
endSpan();
propagateTraceContext();
...
```

这样容易漏，也容易写错。

Dapper 的思路是：

> 大多数服务都会使用一些公共基础库，比如 RPC 库、线程库、消息库、控制流库。  
> 只要在这些库里自动传播 trace context，就能覆盖大部分调用链。

例如：

```text
Application A
  uses RPC library
  uses threading library
  uses messaging library

Application B
  uses RPC library
  uses threading library
  uses messaging library
```

如果这些公共库已经支持 tracing，那么应用代码几乎不用改。

---

#### 2. Dapper 的“近似透明”

原文说：

> remains effectively transparent to application-level software

注意这里不是绝对透明，而是 effectively transparent，也就是“实际上对应用透明”。

因为如果应用使用了标准库：

```text
RPC library
threading library
messaging library
```

那么 tracing 可以自动传播。

但如果应用自己手写网络协议，或者绕过标准库，那么 Dapper 可能追踪不到。

所以“透明”是有前提的：

> 应用主要依赖被插桩的公共基础设施。

这在 Google 这样的大规模环境中是可行的，因为内部通常有统一的：

- RPC 框架；
- 线程模型；
- 消息系统；
- 存储客户端；
- 服务发现；
- 负载均衡库。

### 十二、Cloud Trace 和 OpenTelemetry：Dapper 思想的现代延续

原文说：

> GCP’s Cloud Trace is a publicly available implementation of the Dapper system, accepting traces from any OpenTelemetry compatible source.

这里补充一些现代背景。

#### 1. OpenTelemetry 是什么？

OpenTelemetry 是当前可观测性领域非常重要的开源标准。

它试图统一：

```text
traces
metrics
logs
```

的采集、生成和导出方式。

对于 tracing，OpenTelemetry 定义了：

- trace context 格式；
- span 数据模型；
- SDK；
- API；
- collector；
- exporter；
- propagation 格式。

例如常见的 trace context HTTP header：

```http
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

它包含：

```text
version
trace-id
parent-id
trace-flags
```

这样不同服务、不同语言、不同厂商之间可以交换 trace 信息。

#### 2. 为什么 OpenTelemetry 重要？

在早期，每个公司可能都有自己的 tracing 系统：

```text
Google: Dapper
Twitter: Zipkin
Uber: Jaeger
AWS: X-Ray
Datadog: Datadog APM
```

问题是格式不统一。

OpenTelemetry 的目标是让应用可以用统一方式产生 telemetry 数据，然后导出到不同后端。

例如：

```text
Application
  -> OpenTelemetry SDK
      -> Cloud Trace
      -> Jaeger
      -> Zipkin
      -> Datadog
      -> Tempo
      -> 自建后端
```

这大大降低了迁移和集成成本。

### 十三、Tracing 不只是 RPC 级别：函数级追踪

原文后半段说：

> So far we’ve considered tracing at the level of RPCs, but the concept can be applied to function calls as well.

这是一个很重要的扩展。

前面讲的 trace 多是服务级别：

```text
Service A -> Service B -> Service C
```

但 tracing 的思想也可以用于函数级别：

```text
Function A -> Function B -> Function C
```

---

### 十四、LLVM X-Ray：编译器级函数追踪

原文提到：

> XRay, a feature of the LLVM compiler, uses compiler instrumentation to add trace points at every function entry and exit.

这里的 X-Ray 指的是 LLVM X-Ray，不是 AWS X-Ray。

它的思想是：

> 编译器在函数入口和出口自动插入追踪点。

例如源代码：

```cpp
void checkout() {
  validateCart();
  chargePayment();
  createOrder();
}
```

编译后可能变成类似：

```cpp
void checkout() {
  trace_enter("checkout");
  validateCart();
  chargePayment();
  createOrder();
  trace_exit("checkout");
}
```

当然实际实现不是简单改源码，而是编译器在生成代码时插入桩点。

---

#### 1. X-Ray 的优点

原文说：

> enabling extremely fine latency detail when active and very low overhead when inactive.

这很关键。

##### 活跃时：极细粒度

开启后可以看到每个函数的进入和退出时间：

```text
enter checkout
enter validateCart
exit validateCart
enter chargePayment
enter callBank
exit callBank
exit chargePayment
enter createOrder
exit createOrder
exit checkout
```

这样可以定位到函数级延迟。

##### 不活跃时：低开销

X-Ray 的设计允许桩点存在，但默认不记录。

也就是说，二进制里已经有追踪点，但运行时可以动态开关。

未开启时开销很低。

这比“为了追踪重新编译”方便很多。

---

### 十五、更深的 introspection：动态加日志，不重新编译

原文最后说：

> Other tools can provide even deeper introspection, for example, allowing users to dynamically add logging to their programs without recompiling or redeploying.

这里可以补充一些常见技术。

例如：

```text
DTrace
SystemTap
eBPF
USDT probes
uprobe
kprobe
```

这些工具可以在运行中的系统里动态添加观测点。

例如你可以动态观察：

```text
某个函数被调用时的参数
某个系统调用的延迟
某个内核函数的执行时间
某个用户态函数的返回值
某个 TCP 重传事件
某个文件 I/O 延迟
```

而不需要：

```text
停止服务
修改代码
重新编译
重新部署
```

这在生产环境排障中非常有用。

---

### 十六、把 tracing 放到数据中心背景下理解

这一节虽然短，但它背后对应的是 warehouse-scale computing 的一个核心挑战：

> 单个请求的执行路径跨越大量机器，因此必须把整个数据中心当作一个可观测的系统。

在 WSC 环境里，有几个特点使 tracing 特别重要。

---

#### 1. 扇出非常大

一个用户请求可能触发大量子请求。

例如搜索请求：

```text
User Query
├── Query Parser
├── Spell Checker
├── Ranking Service
├── Ad Service
├── Personalization Service
├── Index Shard 1
├── Index Shard 2
├── Index Shard 3
...
├── Index Shard N
└── Result Merger
```

如果 N 很大，那么即使每个 shard 的 P99 延迟不高，整体 tail latency 也可能很高。

这就是书中其他地方常提到的 tail latency 问题。

Tracing 可以帮助你看清：

```text
哪一片 shard 慢了？
是某个 replica 慢？
是 merge 慢？
是某个下游特征服务慢？
```

---

#### 2. 共享资源多

数据中心里很多服务共享：

- 网络；
- 存储；
- 缓存；
- 数据库；
- 消息队列；
- 机架交换机；
- 电源；
- CPU 核；
- 内存带宽。

一个服务慢，可能不是自身代码问题，而是共享资源争用。

例如：

```text
Service A latency spikes
because Service B is doing a large batch job
which saturates network bandwidth
```

Tracing 结合 metrics 可以帮助发现：

```text
慢请求都集中在某台机器、某个机架、某个存储分片、某个网络路径。
```

---

#### 3. 故障是部分失败

在数据中心里，很少出现“整个系统全挂”的情况，更常见的是：

```text
部分请求失败
部分机器慢
部分副本不可用
部分网络路径丢包
部分服务降级
```

这种 partial failure 很难用简单监控发现。

Tracing 可以按请求维度观察：

```text
为什么这 1% 的请求特别慢？
为什么这些请求失败？
它们是否都经过同一个 shard？
是否都命中同一个缓存节点？
是否都被某个风控规则拦截？
```

---

### 十七、一个更完整的排障例子

假设一个电商网站的 `Buy` 请求 P99 延迟从 300ms 涨到 3s。

#### 第一步：Metrics 发现异常

Dashboard 显示：

```text
Frontend /buy P99 latency: 300ms -> 3s
PaymentService error rate: 0.1% -> 5%
```

你知道出问题了，但不知道根因。

#### 第二步：找一个慢 trace

Tracing 系统里筛选：

```text
operation = /buy
duration > 2s
```

找到一个 trace：

```text
Trace ID: 9c1f2a

Frontend /buy                      3005ms
  AuthService.CheckToken             12ms
  CartService.GetCart                25ms
  InventoryService.CheckStock        40ms
  PricingService.CalculatePrice      30ms
  PaymentService.Charge            2850ms
    FraudService.Evaluate          2800ms
      FeatureStore.GetFeatures     2780ms
        Redis.GET                  2770ms
  OrderService.CreateOrder           35ms
```

#### 第三步：定位瓶颈

从 trace 可看出：

```text
Frontend 慢的主要原因是 PaymentService.Charge
PaymentService.Charge 慢的主要原因是 FraudService.Evaluate
FraudService.Evaluate 慢的主要原因是 FeatureStore.GetFeatures
FeatureStore.GetFeatures 慢的主要原因是 Redis.GET
```

#### 第四步：结合 metrics/logs

继续查 Redis metrics：

```text
Redis node 10.0.1.23 latency spike
Redis BGSAVE running
disk I/O high
```

于是根因可能是：

```text
Redis 节点正在做持久化快照，导致 GET 延迟升高。
```

如果没有 tracing，你可能只知道：

```text
Buy 慢了
```

有了 tracing，你能把用户请求和底层资源事件连接起来。

---

### 十八、Tracing 的常见展示形式：Waterfall 图

现代 tracing 系统经常用瀑布图展示。

例如：

```text
Frontend        |████████████████████████████| 3005ms
AuthService     |█|                           12ms
CartService     |██|                          25ms
Inventory       |███|                         40ms
Pricing         |██|                          30ms
PaymentService  |                           ███████████████████████████| 2850ms
FraudService    |                            ██████████████████████████| 2800ms
FeatureStore    |                             █████████████████████████| 2780ms
Redis GET       |                             ████████████████████████| 2770ms
OrderService    |                                                  ██| 35ms
```

从图中可以很快看出：

```text
关键路径在 Redis GET。
```

这就是 tracing 的直观价值。

### 十九、Tracing 中的关键工程问题

原文没有展开，但实际系统中 tracing 有很多工程挑战。

---

#### 1. 开销问题

如果每个请求都完整记录所有 span，数据量会非常大。

例如一个请求有 500 个 span，每秒 100 万请求：

```text
500 spans/request * 1,000,000 requests/s
= 500,000,000 spans/s
```

这几乎不可能全量存储。

因此 tracing 系统通常需要采样。

---

#### 2. 采样策略

##### Head-based sampling

在请求进入时就决定是否采样。

例如：

```text
采样 1%
```

优点：简单、低开销。

缺点：可能错过稀有错误。

例如 99.9% 请求正常，只有 0.1% 慢请求有问题，随机采样可能抓不到。

---

##### Tail-based sampling

先收集 trace，最后根据结果决定是否保留。

例如只保留：

```text
duration > 2s
status = error
```

优点：更容易保留异常 trace。

缺点：实现更复杂，需要缓存整条 trace。

---

#### 3. Context propagation

Trace context 必须跨进程传播。

例如 HTTP header：

```http
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

或者 RPC metadata：

```text
trace_id: abc
span_id: def
parent_span_id: xyz
```

如果某个服务没有传播 trace context，调用链就断了。

---

#### 4. 异步系统追踪

同步 RPC 比较容易追踪：

```text
A calls B
B returns
```

但异步系统更复杂：

```text
A sends message to Kafka
B consumes message later
```

这时需要在消息里携带 trace context。

例如：

```text
Kafka message headers:
  traceparent: ...
```

否则 trace 会断在消息队列。

---

#### 5. 时钟偏差

分布式系统中不同机器时钟不完全一致。

即使使用 NTP，也可能有毫秒级偏差。

这会影响 trace 的时间排序。

例如：

```text
Machine A clock is 5ms ahead of Machine B
```

可能导致 span 时间看起来不合理：

```text
child span starts before parent span
```

所以 tracing 系统需要处理 clock skew。

---

#### 6. 数据关联

Tracing 最好能和 metrics、logs 关联。

例如一个 span 里包含：

```text
trace_id
span_id
service
host
pod
request_id
user_id
error_code
```

这样你可以：

```text
从慢 trace 找到对应日志
从日志找到对应 metrics
从 metrics 找到对应机器
从机器找到对应硬件事件
```

这才是完整可观测性。

---

### 二十、这一节的核心概念总结

你可以把这一节压缩成下面几个要点。

---

#### 1. Service dashboard 不够

Dashboard 能告诉你：

```text
系统慢了
```

但不能告诉你：

```text
为什么慢
```

---

#### 2. Tracing 追踪一个请求的完整路径

它试图记录：

```text
一个用户请求引发了哪些子请求？
这些子请求之间有什么因果和时间关系？
每一段耗时多少？
哪里出错？
```

---

#### 3. Tracing 是从 monitoring 到 observability 的关键一步

Monitoring：

```text
已知指标异常检测
```

Observability：

```text
通过系统输出推断内部状态
```

Tracing 提供了请求级别的因果视图。

---

#### 4. 两大类方法

##### Black-box tracing

```text
观察网络流量
统计推断因果关系
不需要应用配合
准确性较低
```

代表：

```text
WAP5
Sherlock
```

##### Instrumentation-based tracing

```text
在应用或中间件中插桩
显式传播 trace context
准确性高
需要组件支持
```

代表：

```text
Pip
Magpie
X-Trace
Dapper
```

---

#### 5. Dapper 的关键贡献

Dapper 通过插桩公共基础库，让 tracing 对应用尽量透明。

它插桩的常见模块包括：

```text
messaging libraries
control flow libraries
threading libraries
```

这使大规模部署成为可能。

---

#### 6. 现代实现

GCP Cloud Trace 是 Dapper 思想的公开实现之一。

现代 tracing 常与 OpenTelemetry 结合：

```text
OpenTelemetry compatible source -> Cloud Trace
```

---

#### 7. Tracing 可以到函数级

例如 LLVM X-Ray：

```text
编译器插桩
函数入口/出口追踪
开启时细粒度
关闭时低开销
```

还有 eBPF、DTrace、SystemTap 等工具可以动态加观测点。

### 二十一、可以用一个问题链来记忆这一节

你可以按下面这个逻辑链理解：

```text
1. 为什么 dashboard 不够？
   因为它只能看到聚合症状，看不到请求级根因。

2. 为什么需要 tracing？
   因为一个请求可能跨越很多服务，需要知道它经历了什么。

3. Tracing 追踪什么？
   追踪一个 initiator 引发的所有工作及其因果/时间关系。

4. 有哪两类 tracing？
   黑盒统计推断 vs 插桩显式记录。

5. 黑盒方法优缺点？
   不用改应用，但准确性低、开销可能高。

6. 插桩方法优缺点？
   准确，但需要所有组件支持。

7. Dapper 怎么解决大规模插桩问题？
   插桩公共基础库，让应用尽量无感。

8. Tracing 只能追踪 RPC 吗？
   不是，也可以追踪函数调用，例如 LLVM X-Ray。

9. 更深的可观测性是什么？
   动态加日志和探针，无需重编译或重部署。
```

### 二十二、如果要用一句话概括这一节

可以这样概括：

> 在 warehouse-scale computing 中，单个用户请求可能跨越大量服务器和微服务。服务级仪表盘只能发现异常，而分布式 tracing 通过记录请求在整个系统中的因果路径和耗时，使工程师能够定位根因。Tracing 工具有黑盒统计推断和插桩显式记录两条路线，前者部署容易但准确性有限，后者准确但需要组件支持。Dapper 通过插桩公共基础库实现大规模低侵入追踪，是现代 tracing 系统的重要基础；而 LLVM X-Ray 等工具则把 tracing 推进到函数级和更深层的系统内省。

### 二十三、适合继续深入的问题

如果你想继续深入，这一节可以引出很多值得研究的问题。

#### 1. 为什么分布式系统里“因果关系”比“时间顺序”更重要？

因为不同机器时钟不完全同步。

仅靠时间排序可能错误。

因果关系可以通过 parent-child span 明确表达。

---

#### 2. 为什么全量 tracing 很难？

因为高扇出、高 QPS 下 span 数量巨大。

所以需要在以下因素之间权衡：

```text
数据完整性
存储成本
计算开销
查询延迟
隐私安全
```

---

#### 3. 如果一个服务没有插桩，trace 会怎样？

会出现断链。

例如：

```text
A -> B -> C -> D
```

如果 C 没有 tracing，那么可能只看到：

```text
A -> B -> ??? -> D
```

你知道中间有东西，但不知道细节。

---

#### 4. Dapper 为什么选择插桩公共库？

因为公共库是大多数服务的共同路径。

这样可以以较小成本覆盖大量服务。

这是大规模系统工程中的常见思想：

> 在共享基础设施层做统一能力，而不是让每个应用单独实现。

---

#### 5. Tracing 和 profiling 有什么区别？

粗略说：

```text
Tracing：
  关注一个请求跨服务、跨组件的路径和耗时。

Profiling：
  关注一个进程内部函数、CPU、内存、锁等消耗。
```

例如：

```text
Tracing 告诉你：
  PaymentService 慢了。

Profiling 告诉你：
  PaymentService 里哪个函数占用 CPU 最多。
```

二者结合会更好。

### 二十五、最后给你一个形象类比

可以把数据中心想象成一个巨大的物流公司。

```text
Dashboard 像是总部大屏：
  它告诉你“今天包裹平均延误了 2 小时”。

Tracing 像是给每个包裹装 GPS：
  你可以看到一个具体包裹从下单开始，
  经过哪些仓库、哪些分拣中心、哪些运输车，
  每一站停留多久，
  最终为什么晚点。
```

在 warehouse-scale computing 中，用户请求就是那个包裹。

Tracing 的价值就是：

> 不只是知道系统慢了，而是知道某一个具体请求到底在哪里、因为什么慢了。
