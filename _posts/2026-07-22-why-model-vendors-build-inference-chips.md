## 从推理需求到芯片设计：模型厂商为什么开始造推理芯片

> 一颗推理芯片的起点，不是“需要多少 TOPS”，而是“要用什么模型，在什么流量下，满足什么服务目标，并以什么成本持续运行”。

### 摘要

推理芯片的差异化，几乎从来不在峰值算力，而在于它能否精准匹配某一类工作负载的真实特征——用什么模型、在什么流量下、满足什么服务目标、以什么成本长期运行。这也正是模型厂商纷纷下场造芯片的根本原因：它们手里握着传统芯片供应商最难拿到的一手数据，于是握住了推理硬件的“需求定义权”。

这个转变，其实是训练与推理两种问题形态的差异所决定的。过去几年，AI 芯片的讨论大多围绕训练展开，追逐的是更高的峰值算力、更大的显存、更快的集群互联；而一旦模型进入产品、开始承接真实流量，问题的重心就变了。运营方此时已经清楚地知道用户会输入多长的 Prompt、生成多少 Token、在什么时段形成流量高峰，也知道哪些请求必须在几百毫秒内返回、哪些任务可以排队以换取更低成本。正是这些确定下来的信息，让推理芯片拥有了训练芯片并不明显的专用化空间。

专用化空间来自需求的高度分化。实时语音、搜索、代码 Agent、长上下文分析、离线批处理和端侧模型虽然都叫“推理”，但它们对首 Token 延迟、生成速度、吞吐量、内存容量、带宽、功耗和单位成本的排序完全不同；即便运行同一个模型，只要 batch size、上下文长度、并发量、量化精度、并行方式或服务等级目标有所变化，硬件的最优点也会随之漂移。换句话说，推理市场要找的不是“另一颗更强的 GPU”，而是针对不同负载包络的不同资源配比。

因此，模型厂商做芯片的真正优势，并不是天然比半导体公司更懂物理设计，而是掌握了一组外部供应商极难获得的数据：模型路线图、关键 Kernel、真实请求分布、调度策略、服务等级目标，以及每一美元基础设施投入最终能转化成多少可售卖的 Token。它们把这些信息翻译成芯片的资源约束，再交由芯片、封装、网络和系统伙伴完成工程实现。

本文先建立一套从产品需求到芯片资源的分析框架，再解释 Prefill 与 Decode 这两种数据流的差异，最后用公开的 Llama 3.1 405B 参数构造一个**假想的低延迟 Decode 加速器需求分析**，逐级展示模型特征如何传导到 HBM、计算阵列、片上存储、互联和软件栈。需要强调的是，这个例子不对应任何已发布芯片的真实规格，它的唯一目的，是把 model–system–silicon 协同设计的方法讲清楚。

### 一、起点不是 TOPS，而是工作负载

讨论一颗芯片时，人们最容易先盯着峰值算力——多少 TFLOPS、多少 TOPS（每秒万亿次运算，衡量理论算力上限的指标）、支持 FP8 还是 INT4。但对推理来说，峰值算力只是资源清单里的一项：它既无法单独预测用户感知到的延迟，也无法直接换算成运营方的单位成本。

更合理的起点，是把问题浓缩成一句话：

> **用什么模型，在什么流量下，满足什么 SLA，并以什么成本运行？**

这句话里藏着四组彼此独立又相互作用的变量。

#### 1. 模型：到底要执行什么

模型决定了基本计算图和数据量，具体包括：

- Dense Transformer 还是 Mixture-of-Experts（MoE，混合专家：每个 Token 只激活一部分参数）；
- 总参数量，以及每个 Token 实际激活的参数量；
- 层数、隐藏维度和 FFN 中间维度；
- 注意力机制是 MHA、GQA、MQA 还是 MLA；
- KV head 数量、head dimension 和最大上下文；
- 权重、激活与 KV Cache 的精度；
- 是否存在动态路由、稀疏计算、卷积、视觉编码器或其他特殊算子。

这些特征回答的是“要做哪些计算、搬多少数据”，但它们还不足以单独决定一颗芯片。

#### 2. 流量：这些计算以什么方式到来

推理系统面对的从来不是一个静态的模型文件，而是不断到达、形态各异的请求。因此还必须知道：

- 输入长度与输出长度的 P50、P95、P99；
- QPS、并发量和峰谷比例；
- 实时请求与离线请求的占比；
- 可接受的 batch size；
- Prefix cache 的命中率；
- 长上下文请求的真实比例；
- 多轮对话、Agent 和工具调用形成的状态复用模式；
- 流量是否足够稳定，能否让专用硬件长期维持高利用率。

同一个模型，在 batch=1 的实时对话和 batch=64 的离线生成里会呈现完全不同的计算—访存比：前者往往首先撞上内存带宽的墙，而后者通过权重复用抬高了算术强度，反而可能重新逼近计算瓶颈。

#### 3. SLA：怎样才算服务成功

推理产品里至少有三种不同的“快”：

- **TTFT（Time to First Token）**：从请求到达，到用户看到第一个输出 Token 的时间；
- **TPOT（Time per Output Token）或 TBT**：连续输出 Token 之间的间隔，直接决定“打字机”流式体验的顺滑程度；
- **E2E Latency**：完成整个请求的端到端时间。

除此之外，还要关注 P95/P99 尾延迟、每秒完成的请求或 Token 数、错误率与可用性，以及一个尤其关键的复合指标——goodput，也就是在满足延迟 SLO 的前提下，每台服务器真正能承载的有效请求量。

值得警惕的是，这些指标都不能被单一芯片参数所代表。TTFT 不只是芯片执行 Prefill 的时间，它还包含排队、调度、数据传输、Tokenizer、Prefix cache 和跨节点通信；TPOT 也不由单个 Kernel 决定，而是同时受 continuous batching、KV Cache 管理和 collective communication 的牵制。所以，把某一项芯片峰值直接等同于产品体验，往往会得出错误结论。

#### 4. 经济与部署约束：多快之外，还要多便宜

商业推理最终要回答一连串成本问题：每百万 Token 成本是多少，每瓦、每机架、每美元能完成多少有效 Token，芯片和 HBM 供货是否稳定，数据中心的电力、散热和机架密度是否允许，软件迁移与运维成本有多高，以及这颗芯片究竟只需覆盖一代模型，还是要陪跑连续多代模型。

把这四组变量合起来看，一颗推理芯片真正的目标函数通常不是任何单项峰值，而是：

> **在给定模型、流量和 SLO 下，最大化 goodput、能效和可部署性，同时最小化每个有效 Token 的总成本。**

### 二、为什么推理比训练更容易分化出多条芯片路线

“训练只在乎谁最强，推理在乎很多东西”这句话抓住了大方向，但需要更精确地表达。

前沿训练其实同样在乎成本、功耗、互联、可靠性和供货，并非只盯着峰值算力。真正的区别在于目标函数的集中度：训练任务的目标相对单一——在可接受的稳定性和精度下，以尽可能高的集群吞吐完成一次大规模优化。于是强大的通用算力、成熟的软件生态和可扩展互联会叠加成明显的平台效应，市场自然向少数通用平台集中。

推理面对的负载却高度分散，各自的首要目标几乎互不相同：实时语音优先保证 TTFT、TPOT 和 P99；搜索、推荐和风控需要高 QPS 与可预测延迟；离线生成愿意牺牲单请求延迟，去换更高的 batch 和更低的成本；代码 Agent 与深度研究任务则伴随长上下文、多轮交互和不规则的工具调用；长视频生成更关心持续算力、激活内存和总任务时间；端侧推理又被功耗、面积、成本和本地内存死死约束。

更关键的一点是，推理是一项持续性支出，而非一次性投入。训练完成一个版本便可收尾，推理成本却随用户使用量不断累积。当每天要处理的 Token 达到天文数字时，哪怕每个 Token 只省下极小的能耗或折旧，累计收益也足以支撑一颗定制芯片。这正是推理市场分化的经济根源——它更像是在不同的负载包络中，分别寻找不同的最优资源配比。

### 三、别只按业务名称分类：推理需求有三个维度

把语音、长上下文、视频和端侧直接并列，很容易把业务场景、模型类型和部署位置混为一谈。更清晰的做法，是将它们拆解成三个正交的维度，组合之后才得到真正的硬件需求。

#### 1. 业务与服务目标

| 业务类型 | 首要目标 | 次要目标 | 典型风险 |
| --- | --- | --- | --- |
| 实时语音/对话 | TTFT、TPOT、P99 | 单位成本 | 排队和抖动破坏交互感 |
| 搜索/推荐/风控 | QPS、确定性延迟 | 能效 | 尾延迟与突发流量 |
| 代码与研究 Agent | 长上下文、多轮状态、可用性 | TPOT、成本 | KV Cache 膨胀、工具调用不规则 |
| 离线批处理 | 吞吐量、每 Token 成本 | 作业完成时间 | 资源利用率不足 |
| 内容生成 | 总任务时间、吞吐量 | 显存容量 | 激活峰值和长时间占用 |

#### 2. 模型与算子类型

| 模型类型 | 主要硬件压力 |
| --- | --- |
| Dense LLM | 权重容量、Decode 带宽、矩阵计算 |
| MoE LLM | 总权重容量、Expert 路由、all-to-all 互联、负载均衡 |
| 长上下文模型 | KV Cache 容量与带宽、Attention 计算、状态传输 |
| 多模态模型 | 编码器、LLM、扩散或生成模块之间的异构算子 |
| 视觉/视频生成 | 持续计算、激活内存、时空算子和数据搬运 |

#### 3. 部署位置

| 部署位置 | 主要约束 |
| --- | --- |
| 云端数据中心 | TCO、机架功率、集群互联、可维护性 |
| 边缘服务器 | 本地延迟、有限功耗、有限网络、环境可靠性 |
| 端侧设备 | 面积、成本、几瓦级功耗、共享内存容量 |

只有把三个维度叠在一起，需求才会收敛成具体的硬件指标。举例来说，“端侧实时语音”和“云端实时语音”业务相同，但模型规模、功耗预算、内存系统和成本结构完全不是一回事；同样是“云端 LLM”，低延迟对话与高 batch 离线生成也不能用同一套芯片指标去概括。

### 四、Prefill 与 Decode：同一模型里的两种数据流

一次自回归 LLM 请求通常要经历两个性格迥异的阶段，理解它们的差异，是理解推理芯片设计的骨架。

#### 1. Prefill：处理输入、建立 KV Cache

Prefill 会一次性处理 Prompt 里的多个 Token。由于权重在这些 Token 之间被反复复用，核心线性层通常表现为较大的矩阵乘法，算术强度（arithmetic intensity，每从内存读取一字节数据能支撑多少次浮点运算）较高，因此**这一阶段通常更偏计算瓶颈**。而且 Prompt 越长，Attention 的计算量和中间状态就越吃重。

Prefill 直接影响 TTFT，但两者并不等价：即便芯片把 Prefill 跑得飞快，只要请求还堵在队列里，用户照样会觉得慢。

#### 2. Decode：逐 Token 生成

Decode 则是每一步只为每个请求吐出一个新 Token。在低 batch 时，设备为了这寥寥几个 Token，却要把庞大的权重整份流式读入，权重成本几乎无法被摊薄，因此**这一阶段在低 batch 下通常更偏 HBM 带宽瓶颈**；随着上下文变长，还要额外读取越来越多的 KV Cache。

不过，“Decode 一定 memory-bound”并不是铁律，下面几类因素都会把瓶颈重新推走：batch 增大后权重被更多请求共享，算术强度随之上升；超长上下文抬高了 Attention 计算和 KV 访问的占比；MoE 让每 Token 激活参数变少，却引入了 Expert 路由和网络通信；speculative decoding 一次验证多个候选 Token，改变了矩阵形状和算术强度；量化精度、Kernel 融合和缓存策略会改写实际数据流；而 Tensor Parallel 带来的 collective communication，也可能悄悄成为关键路径。

#### 3. 两阶段对比：一张表看清差异

| 维度 | Prefill | Decode（低 batch） |
| --- | --- | --- |
| 计算形态 | 多 Token 并行、大 GEMM | 少量 Token、反复读取权重与 KV |
| 算术强度 | 高 | 低 |
| 常见第一瓶颈 | 计算 | HBM 带宽 |
| 主要影响的 SLA | TTFT | TPOT |
| 对硬件的首要诉求 | 峰值算力、矩阵吞吐 | 有效带宽、内存容量 |
| 典型优化手段 | 分块 GEMM、算子融合、长序列 Attention 优化 | 提升有效带宽、KV 分页/压缩、continuous batching |
| 重要修正因素 | Prompt 长度、Attention、通信 | batch、上下文、量化、MoE、推测解码 |

#### 4. 为什么会出现 Prefill/Decode 分离

从上表可以看出，Prefill 和 Decode 不只是资源偏好不同，它们服务的指标也不同——前者主导 TTFT，后者主导 TPOT。一旦把两者塞进同一个设备池，一次长 Prefill 就可能卡住正在进行的 Decode，反之亦然。

正因如此，DistServe、Splitwise 等研究提出把两个阶段拆到不同的资源池，各自独立地做并行、调度和容量规划。但这并不意味着分离在所有场景都更优：KV 状态需要跨节点传输，严格的 TTFT、网络条件、请求分布和资源碎片都会侵蚀收益。因此更稳妥的结论不是“所有推理都该分离”，而是“Prefill 和 Decode 已经可以被当作两个独立的容量域来建模”。

### 五、模型厂商做芯片，真正掌握的是什么

传统芯片公司擅长计算阵列、存储层次、时钟、验证、封装和量产；系统公司擅长板卡、电源、散热、网络和机架。相比之下，模型厂商最难被替代的资产是另一种东西——workload knowledge，也就是对工作负载的深度认知。

它们通常掌握六类信息：

1. **模型路线图**：下一代模型是 Dense 还是 MoE，是否会采用新的 Attention、量化或推测解码；
2. **Kernel 画像**：哪些算子最吃时间、带宽和能耗，哪些矩阵形状出现得最频繁；
3. **真实流量分布**：输入/输出长度、并发、峰谷、长尾和缓存命中；
4. **服务系统行为**：batch、调度、KV Cache、并行、容错和多租户策略；
5. **产品价值函数**：TTFT 改善多少会抬高使用率，单位成本下降多少会改变定价或毛利；
6. **软硬件协同能力**：能同时改动模型结构、Kernel、编译器和调度器，而不只是替换一颗芯片。

OpenAI 对其与 Broadcom 合作的 Jalapeño 的公开描述，恰好印证了这种分工：OpenAI 依据模型、Kernel、serving system 和产品需求来定义平台，Broadcom 与 Celestica 则负责芯片实现、网络、板卡、机架和规模化生产。就已公开确认的信息而言，OpenAI 提到的目标包括减少数据搬运、平衡计算与内存和网络资源；而详细的性能报告目前尚未发布——这一点值得读者留意，不宜把方向性表述当成已兑现的规格。

这类合作的本质，并不是“模型公司取代芯片公司”，而是需求定义权发生了转移：

> 模型厂商回答“哪些工作负载最值得被固化和优化”，芯片与系统伙伴回答“如何在面积、功耗、良率、成本和进度的约束下把它实现出来”。

### 六、从服务需求到芯片资源：一套可复用的六步方法

推理芯片的需求分析，可以固化成六个步骤。

#### 第一步：定义 workload envelope（工作负载包络）

关键是给出分布与组合，而不是一个孤零零的最大值：模型族及未来两代路线、输入/输出长度分布、并发和 batch 分布、上下文长度与缓存命中率、在线与离线流量比例、TTFT/TPOT/P99/goodput 目标，以及精度与质量下限。

之所以强调“包络”而非“快照”，是因为模型迭代远快于芯片的设计与量产周期。如果只围绕单个矩阵形状过度固化，芯片很可能在部署当天就已经落伍。

#### 第二步：建立算子和数据流画像

对代表性请求做 profiling，摸清每类 GEMM 的 M/N/K 分布，Attention、MoE、归一化、采样等算子的占比，权重/激活/KV 的字节流量，算术强度（FLOPs/byte），Kernel 间的中间结果是否被写回 HBM，以及不同 batch 和上下文下瓶颈如何迁移。

#### 第三步：选择并行和调度策略

硬件需求高度依赖软件系统，因此要先定下：Tensor/Pipeline/Expert/Data Parallel 如何组合，Prefill/Decode 是否分离，每个模型副本用多少芯片，continuous batching 与抢占策略怎么设计，KV Cache 如何分页、压缩、迁移和复用，以及 collective 的类型、大小和频率。

#### 第四步：做容量和带宽预算

至少要分别算清六笔账：权重容量、单请求单 Token 的 KV Cache、并发 KV Cache、Runtime workspace 和通信 buffer、每次迭代的 HBM 字节量，以及在目标 TPOT 下所需的**有效带宽**——注意是有效带宽，而非 HBM 的标称带宽。

#### 第五步：用 Roofline 判断资源优先级

Roofline（屋顶线模型：用一条“计算屋顶”和一条“带宽屋顶”判断性能到底被什么限制）的价值，不在于精确预测延迟，而在于比较：

```text
可实现性能 ≤ min(峰值计算, 有效带宽 × 算术强度)
```

判断逻辑很直接：如果目标负载长期压在带宽屋顶之下，继续堆 MAC 阵列只会抬高纸面峰值；反之，如果 batch 增大让算术强度显著上升，计算阵列和片上复用就重新变得重要。

#### 第六步：验证总拥有成本

最终要比较的从来不是裸芯片，而是完整系统——每个满足 SLO 的 Token 成本、每瓦 goodput、每机架 goodput、软件迁移与模型适配成本、故障率与冗余和利用率，以及供应链与量产风险。一颗峰值参数更低的芯片，只要能在目标流量下持续保持更高利用率，商业价值反而可能更好。

### 七、案例：为 Llama 3.1 405B 的低延迟 Decode 设计加速器

> **重要说明：**本节是一项基于公开模型参数的假想协同设计练习，不代表 Jalapeño 或任何商业芯片的真实规格。所有带宽目标和并行方案，都只是为了说明推导方法。

#### 1. 已知模型特征

Llama 3.1 405B 是一个 Dense Transformer，公开资料给出的关键参数包括：

- 参数量：约 405B；
- 层数：126；
- 隐藏维度：16,384；
- FFN 中间维度：53,248，使用 SwiGLU；
- Query heads：128；
- KV heads：8，使用 GQA；
- Head dimension：128；
- 最大上下文：128K。

这里最值得关注的是 GQA（Grouped-Query Attention，分组查询注意力）：128 个 Query heads 共享 8 组 K/V，也就是每 16 个 Q head 共用一组 KV。相比 128 个 KV head 的标准 MHA，它把 K/V projection 的参数量和 KV Cache 都大幅削减——这个特征会在后面反复影响芯片的容量、带宽和数据网络设计。

#### 2. 先把服务假设写清楚

假设我们要设计一组面向交互式生成的加速器，先约定如下前提：

- 权重精度：FP8，按 1 byte/parameter 估算容量；
- KV Cache 精度：FP8，按 1 byte/element 估算；
- Tensor Parallel：8；
- 目标业务：在线生成，TPOT 优先；
- 假想 TPOT 目标：30 ms；
- 最大支持上下文：128K，但容量规划必须使用真实的长度和并发分布，而不能假设所有请求同时顶到最大值。

必须强调：下面每一个数字都建立在这些假设之上，一旦精度、并行度或 SLO 改变，结论就会跟着变。真正重要的不是数字本身，而是“先写下假设、再谈芯片”这个动作——没有 batch、并发、上下文和 SLO，就根本不存在唯一的芯片答案。

#### 3. 权重容量：先框定 HBM 下限

FP8 权重的理想容量约为：

```text
权重字节 = 405 × 10^9 parameters × 1 byte ≈ 405 GB
```

若采用 8 路 Tensor Parallel，理想均分后每颗加速器承担：

```text
每芯片权重 = 405 GB / 8 ≈ 50.6 GB
```

**这对芯片意味着什么？** 50.6 GB 只是 HBM 容量的硬下限，而不是最终容量，因为同一块 HBM 还得塞下 KV Cache、激活与临时 workspace、collective communication buffer、模型元数据与运行时开销，以及必要的容量冗余与碎片。换句话说，参数量首先框定的是“HBM 至少要多大”，剩下的空间才留给运行时的动态需求。

#### 4. KV Cache：GQA 如何改变容量

单请求的 KV Cache 可近似表示为：

```text
KV 字节 = 2 × L × H_kv × D_h × S × B_kv
```

其中：2 代表 K 和 V；`L` 是层数；`H_kv` 是 KV heads；`D_h` 是 head dimension；`S` 是上下文长度；`B_kv` 是每个 KV 元素的字节数（本例取 FP8，即 1 byte；若换成 FP16，下面所有 KV 数字都要翻倍）。

代入 Llama 3.1 405B 与 128K 上下文：

```text
KV 字节 = 2 × 126 × 8 × 128 × 131072 × 1 ≈ 33.8 GB
```

约合 31.5 GiB。若 KV heads 能在 8 路 TP 中自然分片，每颗芯片约承担八分之一，即约 3.94 GiB/请求。

**这对芯片意味着什么？** 并发会线性放大这笔容量——一旦一颗芯片同时扛起大量接近 128K 的请求，KV Cache 很快就会吃穿 HBM。因此真实设计必须建立在上下文分布之上，而不能只拿“最大支持 128K”这句宣传语去做规划。GQA 在这里的影响是明确且可量化的：若其他参数不变、把 8 个 KV head 换回 128 个，KV Cache 会暴涨 16 倍。由此可以稳妥地推出几条设计结论：

- GQA 显著缓解了长上下文和高并发下的容量压力；
- 芯片与运行时必须支持高效的 KV 分片和分页；
- KV 精度、压缩和淘汰策略会直接决定可承载的并发量；
- HBM 容量需求必须按“上下文长度 × 并发”的联合分布来算，而不是任何单一维度。

#### 5. 低 batch Decode：为什么带宽最先暴露

在 batch=1 的简化模型里，每个 Decode step 都要访问本芯片上约 50.6 GB 的权重分片。若假想 TPOT 为 30 ms，仅权重读取一项对应的理想有效带宽下限就是：

```text
所需带宽 ≥ 50.6 GB / 0.03 s ≈ 1.69 TB/s
```

请注意，这个数字还没算上 KV Cache、通信和运行时开销，也没有扣除“标称 HBM 带宽无法 100% 转化为应用有效带宽”这一现实折损——真实需求只会更高。

**这对芯片意味着什么？** 由此得到第一条资源结论：

> 对这种低 batch、低 TPOT 的 Dense Decode 负载，HBM 有效带宽和数据通路的优先级，很可能高于继续堆高峰值 FP8 算力。

但故事不会停在 batch=1。当 batch 增大到 `B`，一次权重读取可以同时服务 `B` 个请求，平均到每个 Token 的权重流量近似降到原来的 `1/B`；此时算术强度上升、计算阵列利用率提高，瓶颈可能从带宽重新移回计算或互联。所以芯片绝不能只针对 batch=1 来设计，正确做法是用真实 batch 分布逐段评估：低 batch 区间需要多少带宽、高 batch 区间需要多少计算、在满足 P99 时调度器最多能聚合多大的 batch，以及片上 SRAM 能否靠 tiling 和融合减少 HBM 往返。

#### 6. 长上下文：Attention 会改写算力需求

在每一层的 Decode Attention 中，QK 与 AV 的计算量近似随上下文长度线性增长：

```text
Attention FLOPs ≈ 4 × H_q × D_h × S
```

代入 128K 上下文，每层约为 8.59 GFLOPs，126 层合计约 1.08 TFLOPs/Token；而模型的线性层还要再叠加大致与参数量成正比的计算。**这对芯片意味着什么？** 在极长上下文下，Attention 计算和 KV 流量都会变得显著，“Decode 只是读权重”这个直觉不再成立。于是同一颗芯片至少要覆盖两个 Decode 区间：短上下文、低 batch 时，权重带宽最突出；长上下文或较大 batch 时，Attention、计算与片上复用的重要性明显抬升。

#### 7. GQA 如何影响片上存储和数据网络

8 个 KV head 被 128 个 Q head 共享，意味着一个 KV tile 天然拥有多次复用机会。把这一点翻译成芯片需求，就是：片上存储要提供足够的读写带宽，数据网络要支持低成本的 multicast、局部复制或其他复用机制，Attention Kernel 要允许多个 Q tile 复用同一份 KV tile，编译器则要能根据 batch、上下文和并行方式选择合适的 tile 与映射。

**但不能过度外推。** 不能仅凭“8 个 KV head”就断定“必须有 8 个 SRAM bank”，也推不出某个固定的广播扇出。SRAM bank 数、端口、NoC 和计算阵列布局，还取决于面积、时钟、并发请求、数据布局和其他算子。模型给出的是**复用关系和带宽需求**，微架构给出的则是满足这些需求的一种工程实现。

#### 8. SwiGLU 如何带来融合机会

Llama 的 FFN 由 gate、up、down 三个投影组成，其中 gate 与 up 读取相同的输入。这就带来一个优化机会：可以在软件或硬件中复用输入 tile，并把激活函数和逐元素乘法与矩阵计算融合起来，从而减少中间结果写回 HBM 的次数。对应到芯片上，它诉求的是更大的片上工作集、支持融合的数据流、对胖矩阵和瘦矩阵都能保持利用率的计算阵列，以及能调度不同形状 GEMM 的编译器。

需要说明的是，这只是机会而非硬性约束：它并不必然要求两套物理计算通路，是否并行执行 gate/up，要与芯片面积、其他算子的利用率和功耗一起权衡。

#### 9. Tensor Parallel 如何传导到互联

8 路 Tensor Parallel 让每颗芯片只保存部分权重，但代价是层间需要 collective communication，于是模型需求继续向系统层传导——每层要做多少次 all-reduce 或 reduce-scatter、每次消息多大、通信能否与 GEMM 重叠、目标 TPOT 给通信留了多少预算、拓扑是否对 collective 友好，以及一颗芯片故障会不会拖垮整个副本。

8 个 KV head 让 TP=8 拿到了较自然的 Attention 映射，但这并非严格限制：TP=16 同样可行，只需复制 KV head、进一步切分维度或引入额外通信，区别只在成本。因此正确的结论是：

> **KV head 数会影响并行映射的自然程度和通信成本，但不会唯一地决定并行度。**

#### 10. 最终产出的不是一张版图，而是一份资源优先级

把上述推导汇总，就得到一份候选的资源优先级：

1. 足以容纳权重分片、KV Cache 和运行时空间的 HBM 容量；
2. 面向低 batch Decode 的高 HBM 有效带宽；
3. 面向 8 路模型并行的低延迟 Scale-up 互联；
4. 能覆盖短、胖、瘦各种矩阵形状的 FP8/BF16 计算阵列；
5. 支持 GQA 与 SwiGLU 复用和融合的片上存储与数据网络；
6. 与硬件共同设计的编译器、continuous batching 和 KV Cache 管理；
7. 为下一代模型预留有限但必要的可编程性。

这，才是“从模型特性到芯片设计”的真实传导链：模型参数不会直接告诉你 SRAM 该有几个 bank、芯片周围该摆几颗 HBM，但它能确定工作集、数据复用、带宽下限、通信频率和资源优先级——剩下的，交给微架构去做工程取舍。

### 八、模型特征、系统策略与芯片资源的对应关系

| 上游特征 | 直接影响 | 可能的芯片/系统响应 | 不能直接推出的结论 |
| --- | --- | --- | --- |
| 参数量增加 | 权重容量与读取流量 | 更多 HBM、更多芯片、量化 | 固定 HBM stack 数 |
| GQA/MQA | KV 容量下降、KV 复用上升 | KV 分片、multicast、Attention 专用数据流 | SRAM 必须等于 KV head 数 |

| MoE | 总容量大、激活参数少、路由通信 | Expert Parallel、all-to-all 网络、负载均衡 | 只需要更少算力 |

### 九、专用推理芯片真正可能赢在哪里

专用芯片未必在所有基准上都跑赢 GPU；它更现实的胜算，是在目标工作负载里通过以下五种方式取得优势。

**1. 更匹配的计算—带宽比例。** 如果目标 Decode 长期卡在带宽瓶颈，芯片就可以砍掉一部分为追求通用峰值算力而堆的面积，把资源让给 HBM 接口、片上 SRAM、数据网络和压缩解压单元。

**2. 减少数据搬运。** 能耗和延迟往往不只来自乘加运算，更来自 HBM、片上存储和计算单元之间的数据移动。通过 Kernel 融合、片上驻留、multicast 和更贴合目标模型的数据流，可以把“实际利用率”提上去，而不只是好看的峰值数字。

**3. 与模型共同改变精度。** 模型厂商可以重新训练或校准模型，去适配 FP8、INT8、INT4 乃至自定义低精度格式。通用芯片必须覆盖广泛负载，而模型—芯片联合团队却能围绕自己的质量下限做更激进的取舍。

**4. 与 serving system 共同设计。** 芯片可以从一开始就原生考虑 Paged KV Cache、continuous batching、speculative decoding、Prefill/Decode 分离、Expert routing、模型并行 collective 以及多租户隔离与抢占。真正的收益，往往来自芯片、编译器、Kernel 和调度器的组合，而非某个孤立的硬件模块。

**5. 规模带来的经济回报。** 自研芯片要独自承担设计、验证、流片、封装、软件和量产的全部风险，只有当内部推理量足够大、负载足够稳定、路线图足够清晰时，省下的持续推理成本才可能覆盖这笔固定投入。这也解释了为什么最积极自研芯片的，往往是同时掌握模型、产品和超大规模基础设施的公司。

**但也要看到 GPU 的护城河。** 通用 GPU 的优势恰恰在于生态、灵活性和快速跟进新架构的能力——当模型从 Dense 转向 MoE、从 MHA 转向 MLA，或者引入全新算子时，成熟的编译器、Kernel 库和庞大的开发者社区能让它迅速接住变化。因此专用芯片的胜负手并不是“峰值更高”，而是“负载足够稳定、规模足够大”；否则漫长的流片周期本身，就会变成最大的风险。

### 十、专用化的边界：为什么不能把一切都固化

推理专用化有明确的收益，也有同样明确的风险，二者必须一起看。

**首先，模型变化快于芯片周期。** 从架构定义到规模部署往往横跨数年，而模型可能每几个月就迭代一次，Attention、MoE、量化和推测解码都在持续演进。一颗只适配单代模型的芯片，很可能在部署当天就失去了优势。

**其次，峰值优化可能反噬真实利用率。** 如果为少数规则矩阵形状设计了过于僵硬的阵列，一旦面对长尾形状、小 batch、动态路由或多模型混部，利用率就会掉下来。芯片必须在效率与可编程性之间找到平衡点。

**再次，软件生态可能吞掉硬件收益。** 缺少成熟的编译器、Kernel、Profiler、调度器和故障诊断工具时，纸面优势很难转化成生产环境里的 goodput。模型厂商造芯片，本质上是在给自己揽下一整套新的平台责任。

**最后，互联和内存可能比计算 die 更难啃。** 大模型推理从来不是孤立的芯片问题，HBM 供给、先进封装、Scale-up 网络、机架功率和液冷都会成为系统级瓶颈。只优化计算 die，却不解决数据和状态如何流动，就做不出可真正部署的产品。

综合来看，最佳策略通常不是“为一个模型打造一颗不可更改的 ASIC”，而是：

> **围绕相对稳定的数据流和精度做专用化，同时在模型快速变化的部分保留编程与调度空间。**

### 十一、如何读懂模型厂商的“自研芯片”新闻

当一家公司宣布自研推理芯片时，可以用四组问题，快速判断它的真实技术含义。

**需求是否足够清楚：** 它主要服务哪类模型和产品？优先优化的是 TTFT、TPOT、吞吐、能效还是成本？是内部专用，还是面向行业的通用平台？

**优势究竟来自哪里：** 是更高的 HBM 带宽、更大的容量、更适合 MoE 或 GQA 的数据流，还是更低的精度、更强的互联，抑或更好的调度与软件栈？

**比较是否公平：** 报的是峰值还是实测？是 Dense 还是稀疏算力？是单芯片还是整机架？有没有满足相同的模型质量和延迟 SLO？给出的是吞吐量，还是满足 P99 之后的 goodput？算没算上主机、网络、散热和闲置成本？

**哪些是事实、哪些是推测：** 芯片发布初期通常只公开方向性信息，HBM 数量、封装、片上 SRAM、网络协议和集群拓扑如果没有官方技术报告或可靠的实物分析佐证，就不该被写成已确认的规格。一篇负责任的文章，应该清楚地区分四类信息——**官方公开事实**、**基于公开模型的计算**、**为说明方法而设的假设**，以及**可能的微架构实现**。

### 十二、结论：模型厂商的核心优势是需求定义权

推理芯片市场的分化，表面看是因为“推理场景太多”，更深层的原因在于：推理硬件的最优点由四个因素共同决定——模型与算法、真实流量、serving system，以及产品 SLA 与经济目标。模型结构决定要执行什么，流量和 SLA 决定必须多快地执行，系统策略决定工作如何跨芯片分布，三者叠加，才共同锁定了芯片究竟需要多少计算、容量、带宽和互联。

这也正是模型厂商纷纷踏入芯片设计的原因：它们手握一个完整闭环——观察产品请求、定位系统瓶颈、修改模型和 Kernel、定义下一代芯片，再把硬件收益反哺回产品成本和体验。传统芯片公司拥有实现能力，而模型厂商越来越多地握住了需求定义权。

但要清醒地认识到，从模型到芯片从来不是一条“参数直接决定晶体管”的直线。模型参数能给出工作集、数据流和资源约束，具体的微架构却始终是一组在性能、面积、功耗、可编程性、良率、成本和进度之间反复博弈后的工程选择。

所以，理解一颗推理芯片，最该问的不是：

> 它有多少 TOPS？

而是：

> 它为哪一个 workload envelope 而设计？在什么 SLO 下，它减少了哪一种数据移动或资源浪费？这种优势能否跨越模型迭代，最终沉淀为更低的有效 Token 成本？

当这三个问题都有了答案，我们才算真正读懂了推理需求，也才真正理解了模型厂商为什么开始造芯片。

### 附录 B：关键公式

> 说明：以下公式均为容量与带宽的一阶估算，用于建立直觉和框定量级；实际设计还需计入带宽效率、通信开销、运行时冗余和系统折损。

#### 1. 权重容量

```text
权重字节 = N_params × B_weight
```

其中 `B_weight` 为每个权重的字节数（如 FP8 取 1、FP16 取 2）。

#### 2. KV Cache 容量

```text
KV 字节 = 2 × L × H_kv × D_h × S × B_kv × C
```

其中 `C` 为并发请求数，`B_kv` 为每个 KV 元素的字节数（FP8 取 1，FP16 取 2）。

#### 3. 理想带宽下限

```text
所需带宽 ≥ 每次迭代字节数 / 目标迭代时间
```

实际设计还要再除以可达到的带宽效率，并叠加 KV、通信和系统开销。

#### 4. Roofline

```text
可达 FLOPs/s ≤ min(峰值 FLOPs/s, 有效带宽 × 算术强度)
```

#### 5. Decode Attention 的简化计算量

```text
FLOPs/layer/token ≈ 4 × H_q × D_h × S
```

该式只估算 QK 与 AV，不含 Q/K/V/O projection、FFN、归一化和通信。
